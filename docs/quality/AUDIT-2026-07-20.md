## Open Points (Socratic — systemic impact)

### 1. 🔴 `claimsOfSnapshot` carrega tenant inteiro sem paginação
`resources.ts:claimsOfSnapshot` faz `SELECT … FROM claims WHERE tenant_id = ? ORDER BY seq`
e devolve **todas** as rows. Cliente guarda em `useUi.claimsByCell` (todo o snapshot)
e itera `Object.values(claimsByCell).flat()` em `buildReverseIndexStatic` e em
`ClaimsBrowser`'s reverse-index `useEffect`.

- O que acontece num tenant com **1M de claims**? RAM do server serializa JSON
  inteiro, rede transfere tudo, cliente expande em memória duas vezes (store + reverse index).
- Por que não `LIMIT/OFFSET` ou cursor `since=seq` estilo `graph://history`?
- Esse objeto é fetchado em **cada `graph.rebuilt`** (via `invalidateReverseIndex`
  → `claimsByCell = {}`) e em **cada OpenClaim** (lazy build). É O(n) amortizado
  ou O(n) por abertura?

### 2. 🔴 `presence.typing` sem batching/rate-limit
`typing.ts:presenceTyping` + `signalTyping` em `turn.tsx:135,249` dispara um
tool call HTTP por **keystroke** (textarea `onChange`). Server-side `touchDelta`
itera **todo** `state.presence` (Map) para atualizar `lastDeltaAt` de TODAS as
presenças do user no tenant.

- Para **500 usuários digitando simultaneamente** numa única page, são 500 POSTs/s
  só pra tocar timestamp — e cada um escaneia o Map de presenças inteiro.
  Como isso escala sem debounce client-side maior ou sem agregação server-side por sessão?
- O博览store substitui a Strategy de `changeset.claim` (que já chama `touchDelta`
  internamente). Por que duplicar o caminho caro ao invés de rate-limitar
  client-side a, digamos, 1 emissão a cada 400ms (igual ao sweepTyping)?

### 3. 🟠 `readHistory(0, 1000)` — limite fixo, sem cursor
`history-view.tsx:46` chama `readHistory(0, 1000)`. Nenhum carregamento
incremental, nenhum "load more", nenhum sinal de corte ao usuário.

- Em tenants ativos com muitos commits, eventos > 1000 são **silenciosamente
  descartados** — viés de auditoria exatamente onde LGPD observability importa.
- Por que a UI não oferece `since=< último seq>` incremental, especialmente
  dado que `EventEnvelope.seq` já é monotônico por tenant (D13)?

### 4. 🟠 `claimDraft` engole `JSON.parse(rawJson)` sem guarda
`og.ts:328` faz `JSON.parse(rawJson)` inline, **sem try/catch**. A função
promete retornar `{ ok, reasons, warnings }`, mas JSON inválido lança exceção —
o chamador (`turn.tsx`) recebe rejection não-tratada.

- Que feedback o usuário recebe quando cola JSON malformado? Há toast ou silent failure?
- Como esse contrato se compara ao `res?.ok === false` pattern usado no resto?
  Não seria mais consistente catch → `{ ok: false, reasons: ["JSON inválido: ..."] }`?

### 5. 🟠 `navigateToClaim` — snapshot refetch por dangling ref
`og.ts:520-525`. Click em RefChip de ref ausente → toast + `loadSnapshot()` +
`readSnapshotClaims(true)`. Negative cache é 5s, max 128 refs.

- Snapshot refetch é **caro** (rebootstraps ghost deltas, re-importa changesets).
  Um usuário que explora refs pendentes em massa, ou cujo snapshot é grande
  (ver Open Point 1), degrada a experência para todos na mesma sessão.
- Por que não um `graph://claims?id=<refId>` (lookup pontual) ao invés de
  re-fetch do snapshot inteiro?
- O LRU usa `Map.keys().next().value!` — `!` non-null assertion bypassa TS.
  E se o Map estiver vazio por race condition (clear simultâneo)?

### 6. 🔴 `window.__og_e2e` hooks em produção
`app.tsx:CameraDriver` expõe hooks perigosos **sem guards de `import.meta.env.DEV`**:
```ts
;(window as any).__og_e2e = {
  setNodeResponsibility: (id, r) => useUi.setState(...),
  setNodeDrift: (id, g) => useUi.setState(...),
  setCellAuthority: (cell, a) => useUi.setState(...),
  ...
}
```

- Em prod Qualquer user com DevTools pode escrever
  `__og_e2e.setCellAuthority('auth:P5', 'suspended')` e corromper o estado
  visual local de todos os observers. Não é só debug hook —
  é mutação arbitrária de aggregates (`graph`, `drift`).
- `QueryBar` corretamente gates seu `__og_query_call_count` atrás de `import.meta.env.DEV`.
  Por que `CameraDriver` não segue o mesmo padrão?
- Mesmo que seja só client-side, abusa de `useUi.setState` por **fora do React
  tree** — burla o domínio da store e o single-source-of-truth dos setters
  declarados. Que invariantes_INVALIDAa store (selectedCell seleção atomica,
  setSelectedId + requestCenter combo)?

### 7. 🟡 Layer breach menor: `typing.ts` importa `requireToken` de `tools/session`
`requireToken` é utilitário de domínio de sessão importado como dependência direta
entre tools. Decide se `requireToken` pertence a um `auth/guard` reusável ao invés
de import direto. Add quando: nova tool surgir que precisa validar token (DRY).

### 8. 🟡 `redactFile` heurística deny-by-default?
`resources.ts:redactFile`: para paths fora do `repoPath` e sem `/src/`, cai em
`norm.slice(norm.lastIndexOf("/")+1)` — basename only. Para paths dentro do
repoPath, retorna relativo ao repoPath. Para paths começando com `/`, basename.

- É deny-by-default? A documentação diz "redacts the file path prefix (server
  filesystem layout disclosure)" — mas a lógica é **allow-then-strip**, não
  deny. Se um `repoPath` for mal configurado (relativo, sem `/`), `norm.startsWith(rp+"/")`
  falha e o path absoluto pode ser exposto em parte.
- Inverso seguro: deny tudo que não entra em `/src/` ou `/repo/`. Vale a pena?

### 9. 🟡 `claimsOfCell` aceita `level IN (?, ?)` (P+num, num)
Comentário justifica: claims.level é armazenado como `"P<n>"` (UI) **ou** `"<n>"`
(agent). Funciona, mas cria dois formatos canônicos para a mesma coluna.

- Em algum momento outra ferramenta escreve `level` com terceiro formato?  Onde
  isso é validado p/ write? Se uma migration futura normalizar, a query com `IN`
  break silenciosamente.
- Ponytail:  único ponto de escrita deveria produzir UMA forma canônica. Add quando:
  houver um segundo writer afora `claim.add`.

## Recommended architecture direction (no code)

- **Open Point 1+3**: adotar **cursor pagination** uniforme em todos os recursos
  `graph://` ("claims", "history") com `since=<seq>&limit=<N>` — já usado em
  `graph://history`, erga o mesmo em `claims`. Reverse index constrói-se
  incrementalmente no cliente a partir de páginas trazidas sob demanda.
- **Open Point 2**: `presence.typing` torna-se **cliente-agregado** (debounce
  300-400ms antes do tool call). No server, `touchDelta` deve iterar apenas
  as presenças da sessão tokenizada, não todo o Map (early-return por userId index).
- **Open Point 6**: adotar a regra de **DEV-only instrumentation hooks** em todo
  o codebase (padrão existente em `query-bar.tsx`). Considere um módulo único
  `__og_e2e_bridge.ts` que NÃO é incluído no build de prod (tree-shaking por
  `import.meta.env.DEV`).
- **Open Point 5**: introduzir **recurso pontual** `graph://claims?id=<ref>`
  para ref lookup, evitando re-fetch do snapshot inteiro como fallback de
  dangling refs.
- **Open Point 4+8**: explicitar contratos de erro — `claimDraft` retorna
  `{ ok:false, reasons }` para todos os failure modes, inclusive JSON parse.
